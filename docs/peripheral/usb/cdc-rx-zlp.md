# 10. CDC 接收与 ZLP：CFG_TUD_CDC_RX_NEED_ZLP

`CFG_TUD_CDC_RX_NEED_ZLP` 是 TinyUSB CDC 设备类的编译期宏，决定设备每次给批量 OUT 端点“挂”多长的接收：

- **0（默认）**：一个包；
- **1**：一整块缓冲。

包、事务和短包的基础见 [包、事务与传输类型](/peripheral/usb/transfers)。

## Q: 一次 OUT 传输什么时候算完成？

设备接收前要先告诉控制器“我准备收 N 字节”，这次传输在两种情况下结束：

- 收满 N 字节；
- 收到一个**短包**（小于最大包长，高速下为 512 字节），包括零长包（ZLP）。

传输结束后，TinyUSB 才会把数据搬进 RX FIFO、调用接收回调，然后挂下一次接收。

## Q: 设为 0 和设为 1 有什么区别？

| | =0（默认） | =1 |
|---|---|---|
| 每次挂的长度 | 一个包（512 字节） | `CONFIG_TINYUSB_CDC_EP_BUFSIZE`，例如 8192 |
| 完成时机 | 每收到一个包就完成 | 收满整块缓冲，或遇到短包 |
| 每 8192 字节的中断 / 任务往返 | 16 次 | 1 次 |
| 对主机的要求 | 无 | 数据长度恰为 512 整数倍时要补 ZLP |

默认值慢在第三行：每 512 字节都要走一遍“中断 → TinyUSB 任务 → 拷贝 → 回调 → 重新挂端点”，这段时间里主机发来的包都会被 NAK。一次实测中，默认值下 CDC 接收只有约 7.7 MB/s。

## Q: 名字里为什么有 “NEED_ZLP”？

设为 1 后，设备只把“收满”或“短包”当作结束信号。如果主机恰好发了 512 的整数倍字节（且不到整块缓冲）后就停下，设备既没收满也没见到短包，这次传输就一直挂着：

```usbflow
# =1，缓冲 8192 字节，主机发 1024 字节后停下
H OUT 端点 1
H DATA0 512 字节
D ACK
H OUT 端点 1
H DATA1 512 字节
D ACK 已收 1024 / 8192，没收满也没有短包，传输仍未完成
```

应用层收不到这批数据，直到后面再来数据，或主机补一个 ZLP。所以这个宏的意思是：**打开多包接收，前提是主机会用 ZLP 标记结束**。

## Q: 实际使用要注意什么？

- **速率测试不受影响**：主机连续发大块数据（例如每块 16384 字节），设备每次都正好收满。
- **产品里要小心**：ESP-IDF 的 USB 主机 CDC 驱动 `iot_usbh_cdc` 发送时不设置零长包标志，不会自动补 ZLP。它做主机、设备又打开了这个宏时，长度恰为 512 整数倍的消息会卡在设备里。
- **规避办法**：
  - 保持默认值 0，牺牲接收速率；
  - 应用层保证每条消息长度不是 512 的整数倍；
  - 在主机侧给 OUT 传输加上零长包标志。

PC 作主机时驱动是否补 ZLP 尚未核对，设备要接电脑时需要单独验证。
