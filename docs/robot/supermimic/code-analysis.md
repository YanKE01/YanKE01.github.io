# SuperMimic 代码解析

SuperMimic 用**一个可微的世界模型**训练人形机器人（Unitree G1）的全身控制策略，基于 mjlab。本文先梳理训练配置，下面的维度都按 G1 的 29 个关节计算。

SuperMimic 支持两种任务，共用同一个 Actor（每个任务一个编码器，共用解码器，详见 [Actor 一节](#一个解码器-多个编码器)）：

| 任务 | 输入的目标 | 用途 | 导出文件 |
|---|---|---|---|
| **motion** | 参考动作窗口（未来 0.9 s 的关节角、速度和躯干朝向） | 跟踪一段参考动作，例如从视频中提取的舞蹈、跑步 | `policy_motion.onnx` |
| **velocity** | 速度指令 `[vx, vy, wz]` | 按摇杆指令行走、转向 | `policy_velocity.onnx` |

默认只训练 motion 任务；要训练 velocity 任务，需要修改 `slot_mix`，见[速度指令任务](#速度指令任务)。

::: tip 仿真参数来自 mjlab
SuperMimic **没有自己定义** `sim.mujoco.timestep` 和 `decimation`。`tasks/env_cfgs.py` 直接调用 mjlab 的 `unitree_g1_flat_tracking_env_cfg()`，只改了观测、奖励和随机化，仿真步长和降采样都沿用 mjlab 的设置；SuperMimic 只是在运行时读取 `env.unwrapped.step_dt` 和 `cfg.decimation` 来配置世界模型。

换到其他机器人或修改控制频率时要注意：目标窗口按**帧**取（10 帧、间隔 5 帧），参考动作每个控制步前进一帧，所以控制频率变了，向前看的时间跨度也会变，动作文件的帧率也要与控制频率一致。
:::

```text
仿真（mjlab）──采集──► 回放缓冲区 ──► 训练世界模型（监督学习）
     ▲                                     │
     │                                     ▼
   Actor  ◄──── 在世界模型里"想象"展开，反向传播更新 ────
```

## 控制周期

沿用 mjlab 的 G1 跟踪任务配置：

| 参数 | 值 |
|---|---|
| 物理仿真步长 `timestep` | 0.005 s |
| 降采样 `decimation` | 4 |
| **控制周期** | 0.005 × 4 = **0.02 s（50 Hz）** |

参考动作也是每个控制步前进一帧。世界模型一步预测的就是 0.02 s 后的状态，内部按 4 个子步的方式积分（`substep_coeff = (4+1)/(2×4)`）。

## Actor 与 Critic 网络

配置在 `runners/supermimic_runner.py` 的 `SuperMimicRunnerCfg` 中。

### Actor：多编码器 + 共享解码器

Actor 是 `models.py` 里的 `MultiEncoderAE`。它**仍然是 MLP**，只不过不是一个 MLP，而是**两个 MLP 串起来**：

```text
普通的 MLP 策略：
  [本体观测, 目标] ──► MLP ──► 动作

SuperMimic 的 Actor：
  目标 ──► 编码器 MLP ──► tanh ──► z (32 维)
                                     │
  本体观测 ─────────────────────────► 拼接 ──► 解码器 MLP ──► 动作 (29)
```

名字里的 AE 指这种编码器–解码器（Encoder–Decoder）结构，但它并不像自编码器那样重建输入。

#### 一个解码器，多个编码器

上图的"目标"具体是什么，**取决于任务**。Actor 里其实为每个任务建了一个编码器，共用同一个解码器（名字里的 Multi 就是指这个）：

```text
                ┌─ motion 任务：目标 = 参考动作窗口 640 ─► motion 编码器 ───┐
目标（二选一）──┤                                                          ├─► z (32)
                └─ velocity 任务：目标 = [vx, vy, wz] 3 ─► velocity 编码器 ─┘
                                                                               │
本体观测 93 ───────────────────────────────────────────────────────────────► 拼接 ─► 解码器（共用）─► 动作 29
```

| 任务 | 目标 | 用途 |
|---|---|---|
| `motion` | 未来 0.9 s 的参考动作窗口，640 维 | 跟踪一段参考动作 |
| `velocity` | 机身坐标系速度指令 `[vx, vy, wz]`，3 维 | 用摇杆控制行走 |

- **本体观测和解码器**对两个任务完全一样，区别只在目标走哪个编码器；
- 两个编码器都输出 32 维的 `z`，所以能共用解码器；
- 默认 `slot_mix = {"motion": 1.0, "velocity": 0.0}`，**只训练 motion 编码器**。velocity 编码器虽然建了，但没参与训练。下文不特别说明时，"编码器"都指 motion 编码器。

部署时也是二选一，每个导出的 ONNX 都是"一个编码器 + 解码器"：

| 文件 | 内部结构 | 输入 |
|---|---|---|
| `policy_motion.onnx` | motion 编码器 + 解码器 | 本体观测 + 参考动作窗口 640 |
| `policy_velocity.onnx` | velocity 编码器 + 解码器 | 本体观测 + 速度指令 3 |

velocity 任务的训练方式见下文[速度指令任务](#速度指令任务)。

#### 两个 MLP 的结构由谁决定

两个 MLP 都由同一个函数 `build_mlp(输入维度, 隐层, 输出维度)` 创建，**隐层都取自 `actor_hidden_dims`**，所以两者的隐层完全相同；不同的只是输入和输出维度：

```python
# models.py，MultiEncoderAE.__init__
self.encoders = {
    ts.name: build_mlp(ts.goal_dim, hidden_dims, output_dim=latent_dim)   # 编码器
    for ts in task_specs
}
self.decoder = build_mlp(
    latent_dim + history_length * obs_dim, hidden_dims, output_dim=action_dim  # 解码器
)
```

| | 输入维度 | 隐层 | 输出维度 |
|---|---|---|---|
| 编码器 | 目标维度（由任务决定） | `actor_hidden_dims` | `latent_dim` |
| 解码器 | `latent_dim` + `history_length` × 本体观测维度 | `actor_hidden_dims` | 动作维度（关节数） |

能在命令行修改的只有三个：`--runner.actor-hidden-dims`（默认 `2048 1024 512 256`）、`--runner.latent-dim`（默认 32）和 `--runner.history-length`（默认 1）。目标、本体观测和动作的维度都由机器人和任务自动算出，不需要手动填写。

#### 目标是什么（motion 任务）

这里说的是 motion 任务的目标，velocity 任务的目标只是 3 维速度指令，见下文[速度指令任务](#速度指令任务)。

目标（goal）告诉 Actor **"接下来要做成什么样子"**，来自参考动作（例如从视频中提取、重定向到机器人上的动作片段）。它不是只看下一帧，而是取未来一段窗口：从当前帧起取 10 帧，每隔 5 帧取一帧，即 0、0.1、0.2 …… 0.9 s 后的参考姿态。

每一帧包含：

| 内容 | 维度（G1） | 含义 |
|---|---|---|
| 参考关节角 | 29 | 那一刻每个关节应该转到的角度 |
| 参考关节速度 | 29 | 那一刻每个关节应该转多快 |
| 参考躯干姿态 | 6 | 那一刻骨盆（`pelvis`）的朝向，**相对于机器人当前骨盆朝向**，用 rot6d（旋转矩阵的前两列）表示 |

10 帧合计 (29 + 29 + 6) × 10 = **640 维**，实际排列是先放 10 帧的关节角和速度（580），再放 10 帧的躯干姿态（60）。

世界模型和 Critic 用的完整目标还多一项：每帧参考骨盆位置相对当前骨盆的偏移（10 × 3 = 30），共 670 维。Actor 不用它，因为真机上很难准确知道机器人在世界坐标系中的位置。

#### 本体观测是什么

本体观测（proprioception）是机器人**此刻自身的状态**，只用真机传感器能读到的量（`proprio` 模式，部署必须用这个）：

| 观测项 | 维度（G1） | 来源 | 训练时噪声（均匀分布半宽） |
|---|---|---|---|
| 投影重力 `projected_gravity` | 3 | IMU 姿态换算出的重力方向，表示身体倾斜 | 0.05 |
| 机身角速度 `base_ang_vel` | 3 | IMU 陀螺仪 | 0.2 rad/s |
| 关节角 `joint_pos` | 29 | 电机编码器，减去默认站姿的关节角 | 0.01 rad |
| 关节速度 `joint_vel` | 29 | 电机编码器 | 0.5 rad/s |
| 上一步动作 `actions` | 29 | Actor 上一次的输出 | 0 |

合计 3 + 3 + 29 + 29 + 29 = **93 维**。注意里面**没有机身线速度和高度**，这两项在真机上不好直接测量。

`history_length > 1` 时，会把最近几帧本体观测一起送给解码器，输入变成 `history_length × 93`。

#### 两个网络各管什么

- **编码器**：只看目标，回答"要做什么动作"。640 维的参考动作窗口被压缩成 32 维的隐变量 `z`，可以理解为"动作意图"；
- **解码器**：看 `z` 和机器人当前状态，回答"现在该怎么动关节才能做到"，输出 29 维动作。

拆开的原因主要有两个：

1. **输入悬殊**：目标有 640 维，本体观测只有 93 维。直接拼在一起，目标会占据大部分输入；先压缩成 32 维，解码器的输入就是 32 + 93，两者比较均衡；
2. **多任务共用一个解码器**：不同任务的目标格式完全不同，动作跟踪是 640 维的参考窗口，速度指令只有 3 维 `[vx, vy, wz]`。每个任务配一个自己的编码器，都映射到**同一个 32 维空间**，后面共用一个解码器。这样"怎么走、怎么保持平衡"这些运动能力只需学一次。

#### 以 G1 为例的完整前向过程

下面按部署用的 `proprio` 模式、`history_length = 1` 计算，每个隐层都是 `Linear → LayerNorm → GELU`：

```text
编码器（motion）
  目标 640 ─归一化─► 2048 ► 1024 ► 512 ► 256 ► 32 ─tanh─► z ∈ [-1, 1]³²

解码器（所有任务共用）
  本体观测 93 ─归一化─┐
                      ├─► 拼接 125 ► 2048 ► 1024 ► 512 ► 256 ► 动作 29
  z 32 ───────────────┘
```

| 部分 | 输入 → 输出 | 参数量 |
|---|---|---|
| 动作跟踪编码器 | 640 → 32 | 约 408 万 |
| 速度指令编码器 | 3 → 32 | 约 278 万 |
| 共享解码器 | 125 → 29 | 约 303 万 |

编码器和解码器都用 `actor_hidden_dims = (2048, 1024, 512, 256)` 作为隐层；最后一层不加激活，`z` 再经过 `tanh` 限制在 [-1, 1]。

对应的代码（简化后）：

```python
def forward(self, obs_td):
    # 1. 每个任务用自己的编码器，得到同一空间里的 z
    z = tanh(self.encoders["motion"](self.goal_normalizers["motion"](goal)))
    # 2. 本体观测归一化后展平（history_length 帧拼在一起）
    history = self.obs_normalizer(obs_td["history"]).flatten(start_dim=1)
    # 3. 共享解码器输出动作
    return self.decoder(torch.cat([z, history], dim=-1))
```

#### 训练时怎么同时训练多个任务

- **按批次切分**：`slot_mix` 决定每个任务占多少比例的环境，例如 `{"motion": 0.5, "velocity": 0.5}` 表示前一半环境走动作跟踪编码器、后一半走速度指令编码器。默认 `{"motion": 1.0, "velocity": 0.0}`，**只训练动作跟踪**；
- **隐变量对齐**：动作跟踪编码器是"锚点"。在同一个状态下，把速度指令编码器输出的 `z` 往动作跟踪编码器的 `z` 上拉（均方误差，权重 `latent_bc_weight = 0.1`）。这个损失只更新速度指令编码器，不影响解码器和锚点编码器，保证不同任务的 `z` 含义一致；
- **归一化**：本体观测和每个任务的目标各有一个 `EmpiricalNormalization`，训练中在线统计均值和方差，导出时一起打包。

#### 速度指令任务

velocity 任务让同一个 Actor 也能按速度指令行走，代码在 `tasks/task_spec.py` 的 `make_velocity_task`，参数在 `VelocityTaskCfg`：

| 指令 | 含义 | 默认范围 |
|---|---|---|
| `vx` | 机身坐标系前后速度 | ±1.5 m/s |
| `vy` | 机身坐标系左右速度 | ±0.5 m/s |
| `wz` | 绕竖直轴的转向角速度 | ±3.14 rad/s |

它**没有单独的速度奖励**，奖励仍然是跟踪参考动作（所有任务共用）。训练时的速度指令是从参考动作里算出来的：

1. 取参考动作当前帧前后 25 帧（`window_frames`）的根速度求平均，转到机身坐标系，得到 `[vx, vy, wz]`；
2. 加上均匀噪声（`command_noise = (0.5, 0.5, 0.785)`），再限制在上表范围内；
3. 送进 velocity 编码器，让机器人去跟踪**原来那段参考动作**；
4. 同时用上面的隐变量对齐，把 velocity 编码器的 `z` 拉向 motion 编码器的 `z`。

所以它学的是"给一个速度，回想出动作库里对应速度的那种走法"，走出来的步态像人，但**能力取决于动作数据**：数据里要有前进、后退、侧移、转弯、站立等不同速度的片段，没有覆盖到的速度组合学不好。

::: warning
默认 `slot_mix` 中 velocity 为 0，velocity 编码器不参与训练，但导出时仍会生成 `policy_velocity.onnx`（导出会遍历所有编码器），这个文件**不能用**。要训练它，需把 `slot_mix` 改为例如 `{"motion": 0.5, "velocity": 0.5}`。
:::

#### 部署时只剩一条路径

导出 ONNX 时（`exporter.py` 的 `_SingleEncoderOnnx`），只取**一个**编码器加共享解码器，连同归一化参数合成一张图。所以 `policy_motion.onnx` 里实际就是：

```text
归一化 → 编码器 MLP → tanh → 拼接本体观测 → 解码器 MLP → 动作
```

对部署程序来说，它和一个普通 MLP 策略没有区别：输入一个向量，输出一个动作。

### Critic：普通 MLP

| 项目 | 设置 |
|---|---|
| 输入 | 世界模型状态（68）+ 完整目标（670）+ 仿真参数（33）= 771 维 |
| 隐层 | `(256, 128)` |
| 输出 | 1 维状态价值 |

Critic 能看到特权信息（摩擦系数、质心偏移等），只用于训练，不部署。

### 策略学习

默认用 `ActorCriticPolicyLearner`：

| 参数 | 值 | 说明 |
|---|---|---|
| `horizon` | 32 | 在世界模型中想象展开 32 步 |
| `batch_size` | 4096 | 每次从回放缓冲区抽 4096 个起始状态 |
| `gamma` / `lam` | 0.99 / 0.95 | 折扣因子和 GAE 参数 |
| `lr` | 2e-4 | Adam，`beta2 = 0.95` |

Actor 的损失直接是"想象轨迹回报的相反数"，梯度经过**世界模型反向传播**（BPTT），不是 PPO 那样的策略梯度。展开到最后一步用 Critic 的价值补上剩余回报，Critic 再用 GAE 回报做回归。

## 世界模型

世界模型是 `models.py` 中的 `Dynamics`，一个 MLP：

```text
(当前状态 rep_state, 动作 action, 仿真参数 sim_ctx) ──► MLP ──► 加速度级增量 ──► 积分 ──► 下一状态
```

| 项目 | 设置（GenCoord 表示） |
|---|---|
| 输入 | 状态 68 + 动作 29 + 仿真参数 33 = 130 维 |
| 隐层 | `(2048, 2048, 2048)`，bfloat16 计算 |
| 输出 | 35 维：`[Δv_b(3), Δw_b(3), Δvj(29)]` |

**状态表示**有两种，对应两个任务 ID：

- `SuperMimic-GenCoord-G1`：广义坐标，状态为 `[根高度 z(1), 重力方向 g_b(3), 线速度 v_b(3), 角速度 w_b(3), 关节角 qj(29), 关节速度 vj(29)]` = 68 维；
- `SuperMimic-MaxCoord-G1`：最大坐标，用每个刚体的位置、姿态、速度描述。

网络**只预测速度的变化量**，位置、姿态、关节角都由积分得到，所以预测结果在运动学上是自洽的。

**仿真参数 `sim_ctx`** 来自域随机化，归一化到 [-1, 1] 后作为条件输入：脚底摩擦（1）、躯干质心偏移（3）、编码器零偏（29）。

**训练方式**：从回放缓冲区取长度 8 的片段，从第一帧开始自回归预测 7 步，与真实状态比较。各通道按 Bryson 法则加权（权重 = 1/名义误差²），例如关节角名义误差 0.1 rad、关节速度 3.14 rad/s。

**世界模型环境** `WorldModelEnv` 用 `Dynamics` 代替物理仿真，并用可微的方式算出：

- **奖励**：与 mjlab 相同的动作跟踪奖励；
- **终止**：根高度误差或倾斜误差超过阈值的概率，用 sigmoid 软化（`termination_softness = 0.05`），这样终止也可以求导。

## 模型的输入与输出

Actor 的观测有两种模式，由 `actor_obs` 决定：

| 模式 | 本体观测 | 用途 |
|---|---|---|
| `rep_state`（默认） | 世界模型状态，68 维 | 仿真中训练 |
| `proprio` | 真机传感器能读到的量，93 维 | **部署真机必须用这个** |

本体观测和目标的具体组成见上文 [Actor 一节](#目标是什么)。`proprio` 模式的本体观测定义在 `tasks/env_cfgs.py` 的 `_sensor_actor_group`，目标窗口定义在 `representations.py`（`NUM_GOAL_FRAMES = 10`、`GOAL_FRAME_STRIDE = 5`）。

`history_length` 默认为 1，即只用当前帧；大于 1 时必须是 `proprio` 模式。部署时 Actor 的输入 `obs` 就是 `[本体观测 93 × history_length, 目标 640]`。

**输出**是 29 维动作，实际关节位置目标为 `action × scale + 默认关节角`，交给电机的 PD 控制器。

## 导出到真机

训练时每 `save_interval = 1000` 步保存一次，并上传到 W&B：

| 文件 | 内容 | 真机是否需要 |
|---|---|---|
| `world_model.pt` | 世界模型参数 + 仿真参数归一化 | 否 |
| `actor.pt` | Actor 参数 | 否（ONNX 已包含） |
| `critic.pt` | Critic 参数 | 否 |
| **`policy_motion.onnx`** | 动作跟踪策略 | **是** |
| `policy_velocity.onnx` | 速度指令策略 | 用摇杆控制时需要 |
| `policy_velocity_replay.onnx` | 用参考动作算出速度指令的版本，用于检查仿真到真机的一致性 | 调试用 |

::: warning
只有 `actor_obs = proprio` 时才会导出 ONNX（且动作数据不超过 15000 帧）。默认的 `rep_state` 模式只能在仿真里用，训练真机策略时要加 `--runner.actor-obs proprio`。
:::

`policy_motion.onnx`（`runners/exporter.py`）把**选中的编码器、解码器和归一化参数**合成一张图，还把**整段参考动作**作为常量打包进去：

```text
输入：obs       = [本体观测 93×H, 目标 640]
      time_step = 当前是参考动作的第几帧
输出：actions                  ← 29 维动作
      joint_pos, joint_vel     ← 该帧的参考关节状态
      body_pos_w, body_quat_w, ← 该帧各刚体的参考位姿和速度
      body_lin_vel_w, body_ang_vel_w
```

注意 `obs` 里的 640 维目标要由部署程序自己拼好再输入；输出中的参考状态只是第 `time_step` 帧，沿用 mjlab 跟踪任务的部署接口。ONNX 的元数据中还写入了观测项名称、历史长度、锚点刚体（`pelvis`）和刚体名称列表，部署程序按这些信息组装输入。
